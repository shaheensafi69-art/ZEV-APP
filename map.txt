یک تصمیم مهم در این رودمپ داریم:

این سند را می‌توانی مستقیماً به ایجنت برنامه‌نویسی بدهی.

# بخش اول: قوانین و اصول غیرقابل‌مذاکره پروژه

قبل از هر تغییری، این قوانین باید رعایت شوند:

1. ابتدا تمام پروژه Flutter، بک‌اند، Supabase، Firebase و Cloudflare را بررسی کن.
2. هیچ قابلیتی را که اکنون درست کار می‌کند بدون دلیل خراب یا حذف نکن.
3. هیچ جدول، ستون، اطلاعات کاربر، پست، پیام یا فایل موجودی را بدون بررسی حذف نکن.
4. تمام تغییرات دیتابیس باید از طریق Migrationهای نسخه‌بندی‌شده و قابل بازگشت انجام شوند.
5. قبل از Migration، از دیتابیس Backup قابل بازیابی تهیه کن.
6. از کاربران فعلی و داده‌های واقعی محافظت کن.
7. تمام قابلیت‌ها باید در Backend و Database نیز درست پیاده‌سازی شوند، نه فقط در ظاهر Flutter.
8. برای هر عملیات حساس، Authorization و Row Level Security (RLS) الزامی است.
9. هیچ API Secret، Service Role Key، Firebase Private Key یا رمز عبوری نباید داخل اپلیکیشن Flutter قرار بگیرد.
10. کدهای تکراری، درخواست‌های غیرضروری، Queryهای سنگین و معماری غیراصولی باید شناسایی و اصلاح شوند.
11. هیچ داده یا قابلیت مهمی نباید با اطلاعات ساختگی در محیط Production نمایش داده شود.
12. تمام قابلیت‌ها باید با تست واقعی و گزارش نتیجه تأیید شوند.

**اصل مهم:** قبل از توسعه، وضعیت واقعی هر قابلیت را مشخص کن: سالم، ناقص، خراب یا وجود ندارد.

- مدیریت Logout از تمام دستگاه‌ها
- مدیریت Revoked Session
- بازیابی Session پس از قطعی اینترنت

# بخش چهارم: بازسازی کامل Database

دیتابیس فعلی ZEV کوچک است و باید با حفظ اطلاعات قبلی به یک ساختار حرفه‌ای گسترش یابد.

از PostgreSQL فعلی Supabase استفاده کن. فعلاً نیازی به مهاجرت به دیتابیس دیگری نیست.

## 4.1 استانداردهای دیتابیس

- استفاده از UUID برای شناسه‌ها
- تعریف Foreign Key واقعی
- تعریف Unique Constraints
- استفاده از NOT NULL در فیلدهای ضروری
- استفاده از Timestamps به‌صورت UTC
- تعریف Index متناسب با Queryها
- تعریف Cascade فقط در موارد امن
- استفاده از Transactions
- استفاده از Atomic Operations
- جلوگیری از Duplicate Records
- تعریف Soft Delete در موارد ضروری
- ثبت Created At و Updated At
- ثبت Actor برای عملیات مدیریتی
- استفاده از Migrationهای نسخه‌بندی‌شده

## 4.2 ساختار پیشنهادی جداول

# بخش دوازدهم: Firebase Access برای Agent

Firebase باید در محیط توسعه Agent به شکل امن در دسترس قرار بگیرد.

مراحل:

1. Firebase Project موجود ZEV را شناسایی کن.
2. بررسی کن Android App درست در همان Project ثبت شده باشد.
3. دسترسی Agent را با حساب یا هویت اختصاصی و حداقل مجوز لازم تنظیم کن.
4. در صورت نیاز به Firebase CLI، ورود به حساب توسط صاحب پروژه و با تأیید خودش انجام شود.
5. برای عملیات خودکار و CI/CD از Service Account اختصاصی با مجوز محدود استفاده کن.
6. Firebase Admin SDK را فقط در Backend یا محیط امن اجرا کن.
7. Secrets را در Secret Manager یا Environment Variables امن نگهداری کن.
8. کلیدها و فایل‌های محرمانه نباید وارد Git شوند.
9. هرگز Google Account شخصی صاحب پروژه را با Agent به اشتراک نگذار.
10. برای دسترسی به Production، قبل از هر تغییر حساس تأیید صاحب پروژه لازم است.

فایل‌های لازم برای بررسی:

- pubspec.yaml
- firebase_options.dart
- google-services.json
- AndroidManifest.xml
- MainActivity
- Firebase Messaging Service Configuration
- Backend Firebase Configuration

اطلاعات محرمانه نباید در گزارش Audit چاپ شوند.

# دستور نهایی به Agent

تو مسئول مهندسی و بازسازی کامل ZEV هستی.

هدف صرفاً تغییر ظاهر اپلیکیشن نیست. باید Backend، Database، Authentication، Messaging، Notifications، Media Delivery، Security، Performance و تجربه کاربری را به شکل یکپارچه اصلاح کنی.

ZEV باید از نظر قابلیت‌های اصلی یک شبکه اجتماعی کامل باشد و در طراحی قابلیت‌های جدید، تجربه‌ای هم‌سطح یا بهتر از Instagram را هدف بگیرد.

اما:

- هیچ قابلیت فعلی را بی‌دلیل خراب نکن.
- اطلاعات کاربران را حفظ کن.
- امنیت را فدای سرعت نکن.
- داده‌های واقعی را با داده ساختگی جایگزین نکن.
- از ساخت جداول تکراری جلوگیری کن.
- هر تغییر را تست کن.
- از معماری قابل توسعه استفاده کن.
- عملکرد را اندازه‌گیری کن، نه اینکه فقط ادعا کنی سریع شده است.
- تمام عملیات مالی و شمارنده‌ها باید دقیق و قابل اعتماد باشند.

**اولویت نهایی:**

1. پایداری و حفظ حساب کاربران
2. صحت اطلاعات دیتابیس
3. درست‌شدن کامل Follow، Like، Comment و Post
4. چت و پیام‌رسانی واقعی و سریع
5. Notifications و FCM
6. سرعت تصاویر، ویدیوها و Feed
7. قابلیت‌های کامل Instagram-like
8. سیستم تبلیغات و درآمدزایی
9. امنیت، مقیاس‌پذیری و کیفیت Production

ابتدا Audit کامل انجام بده، سپس Phase به Phase پیش برو و بعد از هر مرحله گزارش بده.

**نتیجه نهایی مورد انتظار:** یک ZEV پایدار، سریع، حرفه‌ای و قابل توسعه که هیچ‌کدام از قابلیت‌های اصلی یک شبکه اجتماعی مدرن را ناقص نداشته باشد.

## چند نکته مهم قبل از تحویل به ایجنت

۱. درباره Firebase: ورود به Firebase باید با دسترسی مجاز و حساب اختصاصی یا Service Account محدود انجام شود. رمز Google شخصی، کلیدهای خصوصی و Service Role را به ایجنت نده.

۲. درباره FCM: احتمالاً منظور تو FCM Token است. ایجنت باید هر سه یا چهار فیلد فعلی را بررسی کند و بدون از دست رفتن توکن دستگاه‌های کاربران، ساختار را یکپارچه کند.

۳. درباره سرعت: سرعت ۰٫۰۰۰۰۰۱ ثانیه برای تمام صفحات هدف واقع‌بینانه‌ای نیست؛ اما می‌توانیم زمان بارگذاری را با Benchmark و بهینه‌سازی جدی به حداقل برسانیم.

۴. درباره دیتابیس: تأکید می‌کنم فعلاً PostgreSQL را نگه دارد. تعداد جدول‌ها به‌تنهایی نشانه حرفه‌ای بودن دیتابیس نیست؛ روابط، ایندکس‌ها، امنیت و صحت داده‌ها مهم‌ترند.

پیشنهاد من: این سند را یک‌جا به ایجنت بده، ولی از او بخواه ابتدا فقط Audit را انجام دهد و گزارش ارائه کند. سپس اجرای مرحله‌ای را شروع کند.
