# ZEV CALLING SYSTEM 2.0 — COMPLETE REDESIGN & ENGINEERING ROADMAP

## PROJECT OBJECTIVE

We need to completely upgrade and redesign the existing Voice Calling and Video Calling system in ZEV.

ZEV is a social media platform with messaging, feeds, videos, friends, and social features.

The current calling system has multiple performance, functionality, UI/UX, and stability problems.

Our objective is to transform ZEV Calling into a premium communication experience comparable to WhatsApp, Instagram, and Snapchat.

IMPORTANT:\
This is not just a UI redesign. It is a complete engineering and product upgrade.

You must inspect the existing codebase, calling architecture, WebRTC implementation, signaling system, media handling, database structure, permissions, and navigation before making changes.

Do not blindly replace working components.

Preserve existing authentication, messaging, user accounts, friendships, database relationships, and other working features.

Do not introduce unnecessary dependencies or break existing functionality.

# PHASE 1 — CALL ENGINE & CONNECTION PERFORMANCE

## 1. Extremely Fast Call Connection

CURRENT PROBLEM:\
When one user calls another user, the receiver answers, but the call takes approximately 5–6 seconds to establish.

REQUIREMENTS:

- Minimize call connection time.
- Establish the media connection immediately after the receiver accepts.
- Optimize WebRTC peer connection initialization.
- Optimize SDP offer/answer exchange.
- Optimize ICE candidate collection and exchange.
- Avoid unnecessary initialization delays.
- Implement ICE candidate trickling where supported.
- Optimize signaling message delivery.
- Prevent duplicate connection initialization.
- Handle network changes intelligently.
- Implement reliable STUN/TURN configuration.
- Support TURN over UDP and TCP/TLS where appropriate.
- Implement ICE restart when necessary.
- Handle connection failures and automatic recovery.

The target should be to make the call feel almost instantaneous after acceptance.

Measure actual connection performance rather than assuming it is fast.

Track:

- Call initiation time.
- Receiver notification time.
- Answer response time.
- ICE gathering time.
- ICE connection time.
- First audio packet time.
- First video frame time.

Do not sacrifice connection stability for speed.

## 2. Instant Video Rendering

CURRENT PROBLEM:\
After accepting a video call, the remote camera sometimes takes 10 seconds to appear.

REQUIREMENTS:

- Display the remote video as soon as the first usable video frame arrives.
- Start audio and video negotiation efficiently.
- Optimize camera initialization.
- Optimize remote video track handling.
- Avoid waiting for unnecessary media operations.
- Prevent multiple unnecessary renderer initializations.
- Handle track replacement correctly.
- Display a professional loading state while the remote video initializes.
- Avoid displaying a broken or frozen video component.
- Ensure audio starts without waiting for video rendering.

The first remote video frame should appear as quickly as technically possible.

## 9. Independent Camera Filters for Each User

When one user activates a filter, the filter incorrectly affects the other user's video.

User B must not have their own camera affected by User A's filter selection.

The correct media pipeline should be:

Camera Input → Local Effects Processing → Outgoing Video Track → Remote Participant.

The local preview and outgoing video must show the same processed image.

Never apply a local camera effect directly to the remote participant's camera.

## **۲. معماری تماس گروهی را جدی بگیر**

اگر ZEV از WebRTC استفاده می‌کند، برای تماس گروهی بزرگ بهتر است معماری SFU را بررسی کنی. این معماری معمولاً نسبت به اتصال مستقیم همه کاربران به یکدیگر مقیاس‌پذیرتر است.

## **۳. بک‌گراند و پنجره شناور**

این قابلیت‌ها فقط با طراحی UI حل نمی‌شوند. باید چرخه عمر تماس و قابلیت‌های Native اندروید و iOS درست پیاده‌سازی شوند. همچنین پنجره شناور داخل ZEV با Picture-in-Picture سیستم‌عامل دو قابلیت متفاوت هستند.
